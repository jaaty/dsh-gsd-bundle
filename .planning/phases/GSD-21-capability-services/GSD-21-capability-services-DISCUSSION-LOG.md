# Phase 21: capability-services — Discussion Log

Interview for phase 21 (capability-services, DEGR-01 + DEGR-03). Grey areas identified from a deep dive of the bundle against the Cordis runtime: (1) the central tension that Cordis coeffects are REQUIRED dependencies (a fiber deactivates if an inject key is missing) whereas graceful degradation needs OPTIONAL skip-if-absent dependencies — so the design hinges on who declares coeffects on capabilities and how; (2) capability granularity for core-tools, which mixes model-bound orientation tools with a model-agnostic job tool; (3) capability descriptor richness; (4) the mechanism for reactive command unregistration; (5) capability key naming. The user raised a forward-looking question: whether the split should support a future scrum-style (initiatives/epics/stories/subtasks) swap of the work-tracking model. Analysis showed gsd_init/gsd_new_milestone/gsd_status/gsd_progress are model-bound (the surface a scrum swap would replace) while gsd_job is model-agnostic, so the capability boundary should split along that line. Decisions confirmed by the user: split gsdOrient + gsdJobs; rich descriptor; persona polls via ctx.get (no coeffects on capabilities); per-command sub-fibers injecting the capability for reactive command unregister; camelCase keys. Scope correction recorded: phase 21 is purely additive on the registration/reactivity layer (publish capabilities + wire commands to them via coeffect sub-fibers); persona/gsd_status rendering from capabilities is phase 22, so persona is untouched here.
